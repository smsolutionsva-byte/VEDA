# VEDA v0.3.7 Release Notes

## Headline

VEDA v0.3.7 fixes the core evidence-decomposition bug that caused daily construction reports to collapse into a single whole-page observation, then contaminate matching with a page-level discipline/classification. The release introduces atomic observation extraction, deterministic exact-identity resolution, safer date handling, and stronger provenance tracking for evidence, issues, and progress records.

## Root cause fixed

The root problem was in `veda/pipeline/extract.extract_evidence()`: every non-tabular document was being split on blank lines and emitted as one `evidence` record per text block. A Daily Construction Report whose PDF text had no blank-line breaks, or whose table had been flattened by `pypdf`, collapsed into a single row containing the entire page.

That single row then:

- was classified with `guess_discipline()` over the whole page, causing misleading labels such as `Welder` from a manpower line;
- was passed as one unit into `linking.link_evidence()`, where the retrieval engine tried to match a whole page to a single activity;
- still produced placeholder `[page 1]` rows even when extraction was effectively image-only.

The fix keeps the six domain entities separate (`files`, `evidence`, `activities`, `evidence_links`, `proposals`, `reviews`), but makes the bug impossible at the source: a document is decomposed into atomic observations instead of page-sized blocks.

## What changed

### Document decomposition engine

A new decomposition engine in `veda/pipeline/documents.py` now handles:

- text acquisition
- document classification
- sectioning
- atomic typed observations
- routing tags for downstream handling

This is intentionally generic and not project-specific. It routes free-text documents into structured evidence variables instead of letting a full page become one observation.

### Evidence schema and routing

The `evidence` table gains 12 new fields and indexes, including:

- `observation_type`
- `document_type`
- `section`
- `row_index`
- `raw_text`
- `raw_values_json`
- `extraction_method`
- `extraction_confidence`
- `observation_key`
- `raw_date`
- `date_interpretations_json`
- `activity_description`

The `state` values now include `context`, `issue`, and `deferred`.

The free-text extraction path delegates to `documents.decompose()`, and chat/JSON/tabular paths now tag `observation_type` and `observation_key`. Non-semantic observation types skip action/discipline classification.

### New dataflow

The release changes the pipeline from this:

```text
FILE → read text → split on blank lines → 1 evidence row per block
     → classify whole block → hybrid_search(whole block) → 1 activity match
     → [page 1] placeholder still produced a row and still ran the matcher
```

to this:

```text
FILE
 → TEXT ACQUISITION            documents.acquire_text
     placeholder / image-only / too-short → ExtractionRequired
       → file.extract_state='extraction_required', NO evidence, NO match, review
 → DOCUMENT CLASSIFICATION     documents.classify_document → document_type
 → SECTION EXTRACTION          documents.segment
     report_metadata | work_progress | manpower | equipment | target | issue | weather | signoff
 → ATOMIC OBSERVATION EXTRACTION
     each work-progress row → 1 ACTIVITY_PROGRESS observation
     each manpower/equipment row → 1 context observation
     each issue row → 1 ISSUE observation
 → OBSERVATION-TYPE ROUTING
     activity_progress / general → activity resolver
     issue → issue/risk engine
     manpower/equipment/weather/report_metadata/signoff/target → stored as context, never matched
 → ACTIVITY RESOLUTION (per observation)   linking.link_evidence
 → VALIDATION / HUMAN REVIEW   per ambiguous observation, never per page
```

### Exact-identity matching

The resolver is now filtered to `observation_type IN (activity_progress, general)` or legacy `NULL`. Exact matches are handled deterministically before retrieval gets a chance to drift.

A normalised activity description that exactly matches one schedule activity name (with location tokens used to disambiguate repeated names) becomes candidate #0 with `identity_exact=1`, even if retrieval did not rank it highly.

This separates:

- identity confidence (how strongly the evidence matches the exact activity identity)
- schedule-write authority (whether the system is allowed to write a schedule change)

The risk policy retains `schedule_write_allowed=False` for identity-only matches, but the confidence can still be high and explicit. For exact-identity matches with no validator failure, `risk.assess` is overridden to `link_identity_only`, and the calibrated probability is floored at `0.97` with `mode="deterministic_identity"` and `calibration_is_empirical=0`.

This structurally prevents contamination: `Welder` only appears in manpower context observations, which never enter the activity resolver.

### Date interpretation safety

The date layer now interprets ambiguous dates without mutating the original raw value.

`dates.interpret(raw, context_dates)` returns:

- `raw`
- `normalized`
- `date_format_interpretation`
- `confidence`
- `reason`
- `ambiguous`
- `interpretations[]`

Every valid calendar interpretation is preserved and ranked by proximity to neighbouring dates and schedule bounds. A raw value like `10.03.2017` remains raw while being interpreted as `2017-10-03` with a reasoned explanation that `MM.DD.YYYY` is preferred over `DD.MM.YYYY` based on context.

### Deduplication and idempotency

The file-level SHA-256 behavior remains unchanged, but observation-level deduplication is now deterministic by `observation_key`.

The reconciliation step upserts observations by key, keeping unchanged records stable so `evidence_links` and human decisions survive re-extraction. Observations no longer produced are removed unless a human decision depends on them; legacy keyless rows are replaced once the new keys are established.

## Tests and verification

- `tools/make_project_218_fixture.py`

### Acceptance results

All 22 acceptance checks pass, with 0 failures.

Key proofs from the Project 218 fixture include:

- more than one observation extracted from the DCR: 21 observations
- 6 work-progress observations resolved to 6 schedule activities
- six exact matches retain high identity confidence at 0.97
- manpower terms do not contaminate workflow activity matching
- issue rows are extracted independently and linked to the correct affected activity
- `10.03.2017` is preserved as raw while the normalized interpretation remains correct
- placeholder-only image documents are correctly marked as `ExtractionRequired`
- re-uploading the same source remains idempotent with stable keys
- review flow is per observation, not per page

## Operational scope

This release intentionally narrows the problem surface and makes failure modes safer:

- heavily merged or rotated PDF cells may still under-segment and surface as `extraction_required` instead of contaminating the match flow;
- exact-identity resolution requires straightforward normalisation of the field description to the schedule activity name;
- issue-to-activity matching remains heuristic for vague writeups;
- date interpretation covers common numeric and month-name patterns, but not all relative or quarter/week forms;
- `observation_key` is application-level and not yet enforced by a DB-level unique constraint;
- manpower/equipment observations are now captured and typed as context, but they do not yet drive a dedicated resource-reconciliation subsystem.

## Summary

v0.3.7 is the release that corrects the evidence pipeline at its root: VEDA no longer treats a whole document as one observation. It now decomposes documents into atomic typed observations, resolves exact identities deterministically, keeps raw evidence and interpretations separate, and prevents manpower/context noise from polluting schedule matching.
